# Expand SimsDataSDK to cover the studio's remaining game-data extraction

## Goal and context

Sim Overhaul Studio reads The Sims 4 installation, Mods, saves and Tray to build editable household and Sim views. We would like SimsDataSDK to own reusable game-format parsing and game-data interpretation, so the studio can consume documented models instead of maintaining supplemental parsers and pre-extracted JSON. Studio-specific UI, project storage, matching decisions and script-mod behavior can remain in the studio.

This request is based on the SDK checkout bundled with the studio (package version `0.9.0`, commit `8b9793d6a601d001d1e82b3b4ef0004eb7f32311`). The checkout already supplies DBPF/RefPack, static catalogs, saves, Tray, starter households, many relationship models, family trees, diagnostics, icons and save/Tray artwork. Please treat the items below as incremental requests, not a request to reimplement those capabilities. Some can be addressed by documenting an existing public API if it already provides equivalent results.

The paths below refer to the studio repository. Proposed names are illustrative; equivalent APIs are welcome. All game, save and Tray access should remain read-only for this work.

## 1. Supplemental catalog definitions and tuning metadata — high priority

The studio builds most definitions from the SDK, then scans SimData resources for missing kinds and scans mod XML headers (`backend/catalog.py:_scan_simdata_package`, `_scan_mod_package`, `build_catalog`). It also merges `data/xml_tuning_items.json`, generated by `tools/build_xml_catalog.py`. The DBPF access in those scanners already goes through the SDK-backed `backend/dbpf.py`; classification and interpretation remain local. The scans use token/name heuristics and can miss or misclassify data.

**Requested**

- Provide typed catalog entries for skills/statistics, degrees, identity and occult definitions, objectives and relationship-track definitions, including stable IDs, tuning names, localized labels, icon keys, pack and source provenance. Distinguish actual skills from other statistics and represent degree major/honours where available.
- Surface useful restrictions (age, species, occult), career level/track/branch links, aspiration track labels and relevant trait/reward relationships when encoded in tuning. Preserve unknown values rather than turning a name-based guess into a fact.
- Include installed game and mod content, XML and binary where supported, with deterministic override/load-order behavior and diagnostics for unsupported resources. Make mod provenance clear, including package path and whether the definition overrides another.
- Provide pack codes and, where reliably available, display labels; document localization and fallback behavior.

**Acceptance:** a consumer can enumerate these kinds without scanning raw SimData/XML or merging the studio's supplemental JSON; known IDs, labels, restrictions, source and overrides are regression-tested against representative base-game, pack and mod fixtures. Unsupported formats or unknown metadata are explicit, not silently interpreted as absence.

## 2. Skill XP curves — high priority

`backend/skillcurve.py` selects hard-coded curves based on tuning names; `backend/sdkconvert.py` and `backend/templatedata.py` use them to turn raw XP into displayed levels. The SDK's `SkillLevel` documents that threshold tables are not modeled. This affects premades and imported save/Tray Sims.

**Requested:** expose a shared skill definition/curve and conversion API for all three sources, preferably resolving thresholds from game data, including adult, child, toddler, extended and custom/modded curves. Preserve raw XP, indicate unknown/unresolved curves, define threshold boundaries and maximum levels, and distinguish an unassigned/default XP floor from a genuinely assigned skill when the source supports it. Do not silently apply a standard curve to unknown skills.

**Acceptance:** boundary tests for each supported curve, including 100 XP baseline handling, and consistent results across starter, save and Tray models. Useful local checks include Bella Goth's level-2 skills and Tybalt Capp's Painting 8, Piano 6, Swordsmanship 7 and Charisma 9, subject to installed game version and source data.

## 3. Complete premade world and provenance — high priority

`backend/templatedata.py` combines SDK premade models, starter-household records and catalog data. It reparses raw starter records for STBL-keyed names (fields 55/56), merges skills/careers/aspirations and relationships, and falls back to bundled ancestor/dynasty metadata. `backend/tray.py`, `clubs.py`, `secrets.py`, `households.py` and `npc_relations.py` add further facts and inferred links from pre-extracted JSON. Those JSON files are produced by `tools/build_premade_*.py`, `build_household_relations.py`, `build_npc_relations.py` and related tooling.

**Requested**

- Resolve starter-member first/last name STBL keys through the selected locale, preserving keys and unresolved values; expose household names, descriptions and lot associations where present.
- Expose premade clubs and membership, starting milestone fixups, secrets and participants, dynasty seed details and member roles, ancestor titles/regions/ranks/death data, and structured pronoun and gender-identity data when encoded. Keep identity distinct from physical frame and preserve unknowns.
- Expose career level-to-career/track links, specializations and aspiration track information sufficient to construct the starting state without a separately generated career overlay.
- Expose household and cross-household relationship setup, relevant loot/bit operations, family fixups, scores/ranges and sentiments with direction and IDs. Make explicit which are direct data, conditional operations, inferred links or consumer-chosen defaults. Do not present speculative family edges or runtime-dependent outcomes as facts.
- Offer a documented way to join template IDs, starter Sim IDs and household IDs, with collision/unresolved diagnostics. A composed premade-world view would be useful, but individual models and helpers are also acceptable.

**Acceptance:** an application can build the available premade starting data without the studio's raw-name parser or bundled `premade_careers`, `premade_milestones`, `premade_clubs`, `premade_secrets`, `premade_dynasties`, household-relationship and NPC-relationship overlays. Tests cover STBL-keyed names, multiple households, a cross-household pair, an ancestor and at least one conditional or directional relationship. Source limitations and unresolved links remain visible.

## 4. Tray discovery, names and aspirations — high priority

The SDK already provides Tray models and readers, but the studio groups Tray files by filename itself (`backend/tray.py:_scan_groups`) and its normal list view uses a local raw-byte/protobuf name heuristic (`_name_only`, `backend/protobuf.py:fast_sim_names`). It also searches printable strings in `.trayitem` files and guesses which Sim an aspiration belongs to (`_apply_trayitem_aspirations`).

**Requested:** provide a documented, efficient household-library listing API that groups associated `.householdbinary`, `.trayitem`, `.sgi` and `.hhi` files, exposes identifiers, names, timestamps and available images, and reports per-file failures without discarding the rest of the library. Ideally support a lightweight listing mode. Expose per-Sim aspirations when the file actually encodes a reliable association; if only text is present, expose that as unassociated evidence rather than assigning it by proximity. Document any data loss or unsupported wrapper/version.

**Acceptance:** the studio can list the same supported households using SDK results without reading raw household bytes or reconstructing filename groups. Tests include malformed and incomplete groups, duplicate/ambiguous names and a `.trayitem` without a trustworthy aspiration-to-Sim link.

## 5. Save/Tray completeness and SimInfo — medium priority

The studio uses SDK readers for detailed saves and Tray, and converts the models to its own UI format. The existing studio feature request reports cases where save relationships were missing and calls out additional baked `SimInfo` sections; those observations are historical and should be reproduced against the current checkout before being treated as confirmed defects.

**Requested:** verify complete decoding of available relationship targets, directional tracks, bits and sentiments in representative saves and Tray files, and expose explicit diagnostics when a tracker is unsupported. Extend `SimInfo` beyond its currently documented partial trait-list reader to preferences, skills, careers, degrees and aspirations where the format actually contains them. Keep raw values, completion state and provenance, and distinguish missing data from an empty tracker.

**Acceptance:** synthetic fixtures and, where possible, anonymized real-world regressions show populated relationships when present and sensible missing/unknown states otherwise; any unsupported `SimInfo` section is documented. Skill-level conversion uses the shared API above.

## 6. Artwork and icons — medium priority

The SDK already offers `read_tray_image`, `decode_artwork`, `Artwork.to_png()`, `Sims4Workspace.icon_for()` and game-image PNG conversion. The studio still has:

- A Tray wrapper fallback and tolerant handling of JPEGs without EOI (`backend/images.py:read_artwork`); alpha-mask presentation processing also lives there.
- A recursive package scan for premade household composites (`backend/premade_art.py:find_portraits`), using the SDK-backed DBPF reader and SDK artwork decoder.
- A DDS fallback when SDK icon conversion fails (`backend/gameicons.py:icon_path`); whether it is needed for currently supported inputs should be verified with fixtures.

**Requested:** expose premade household composite lookup by template/resource key through the SDK's package index/load order; return the existing `Artwork`-style JPEG/mask representation. Support observed valid Tray wrapper variants, with tests. For incomplete JPEGs, provide an explicit tolerant mode or documented recoverable diagnostic rather than accepting arbitrary malformed data silently. Investigate unsupported icon formats against actual failures, and document supported formats. Optional configurable mask rendering is useful; UI-specific crisp-alpha and portrait cropping may remain local.

**Acceptance:** callers find and decode available premade composites and supported Tray variants without a separate package scan or wrapper decoder. Tests cover missing images, load-order conflicts, masks, malformed data and tolerant-vs-strict behavior. Preserve raw image data and avoid inventing per-Sim crops.

## 7. Public resource, diagnostics and performance contracts — medium priority

- Document supported low-level APIs for package/resource enumeration, SimData/combined-tuning access, localization, and metadata/provenance so consumers do not depend on private fields or re-scan packages when a model is not yet available.
- Extend structured diagnostics to include stage, source path/resource key, recoverability and unsupported format where feasible. Batch operations should retain successfully decoded items alongside failures.
- Keep cache invalidation, locale, installed packs, mod changes and package load order explicit. Support progress/cancellation for expensive builds and lightweight library listing where practical.
- Preserve backwards compatibility or document migration, and include JSON serialization for new public models and unknown values.

**Acceptance:** documented examples cover an install with mods, a Tray library containing one bad file, source provenance and a cached refresh after a content change; regression tests verify deterministic results and diagnostics.

## Scope and implementation order

Suggested order: (1) catalog definitions and XP curves, (2) premade identity and world data with provenance, (3) Tray listing and aspiration evidence, (4) artwork coverage, (5) save/SimInfo completeness and public performance contracts. These can be split into separate issues.

Exporting the studio's `.ts4script`, UI formatting, project persistence, manual editing and app-specific inference policies are not prerequisites. A reusable package writer or validation API could be discussed separately; no save/game write support is required for this request.

## Validation and migration

- Compare SDK-only results with the studio's existing output on a documented game version and installed-pack set; report differences by ID and provenance rather than relying on totals alone. Existing datasets and counts are historical fixtures, not proof of current behavior.
- Add small redistributable or synthetic format fixtures plus optional local-install integration checks. Test missing packs, mods, localization, malformed inputs, partial data and load-order conflicts.
- Mark API support complete only after the studio can remove the corresponding scan/overlay while retaining expected behavior; UI transformations and explicitly labeled heuristics can stay local.
- Please document any data that the game does not actually encode, or that can only be determined at runtime, instead of filling it with guessed values.
